# HTTPS Kafka gateway source candidate

Run `python -m gateway.server` with `PYTHONPATH=deploy/cloudflare` and mounted files named by `GATEWAY_TLS_CERT_FILE`, `GATEWAY_TLS_KEY_FILE`, `GATEWAY_SECRETS_FILE` and `GATEWAY_DATABASE_FILE`; set `GATEWAY_KAFKA_BROKER` to a loopback Kafka sidecar and `GATEWAY_KAFKA_TOPIC` to a dedicated `g1b4-` topic. The secret file is a JSON mapping of key IDs to HMAC secrets of at least 32 characters. Mount it privately; do not put values in repository configuration. During rotation, accept old and new keys together, switch the dispatcher to the new key ID and secret, then remove the old key after its 30-second request window and retry budget. Restart the gateway for each mapping change.

The current source binds to loopback and uses one SQLite file for nonces, receipts and attempts. Two local gateway instances sharing that file reject the same nonce across instances and restarts. This is a **single-host source candidate**: a distributed deployment needs a reviewed, shared transactional store for nonce claims and receipts, a durable backup/retention policy, an authenticated Kafka transport or private broker sidecar, and ingress/network policy. Do not expose this process publicly or treat the local SQLite evidence as cross-host qualification.

The client must use an `https://` URL with normal CA and hostname validation. The HMAC covers timestamp, nonce and exact request bytes. Broker acknowledgment and receipt persistence precede HTTP 200. Retried delivery can publish more than once if the broker acknowledged but the receipt was not committed; consumers must deduplicate stable event IDs. The source does not log secrets or event bodies. Cloudflare production dispatch remains disabled.
