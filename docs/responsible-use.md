# Responsible Use

> This project is **not** a medical, psychological, neurological,
> workplace-surveillance, or diagnostic system. It is an educational MLOps
> demonstration built on entirely synthetic data (see
> [`data-card.md`](data-card.md)).

## What this system is

An end-to-end demonstration of an MLOps pipeline — data versioning, model
training/registry, containerized serving, Kubernetes deployment, and
observability — applied to a toy classification problem (LOW/MEDIUM/HIGH
"cognitive load" from four numeric inputs).

## What this system is not, and must not be used for

- **Not a validated psychometric instrument.** The labels it was trained on
  are generated by a hand-written formula, not derived from any peer-reviewed
  cognitive-load model or human study.
- **Not for employee evaluation or workplace monitoring.** Do not wire this
  API into any system that scores, ranks, or reports on real employees'
  focus/productivity.
- **Not for medical or psychological decisions.** Do not use predictions to
  diagnose, screen, or triage any real person's mental state.
- **Not for academic discipline or accommodation decisions.**
- **Not for any decision with material consequences for a real person.**

## Data minimization, if this were ever extended to real users

None of the following is implemented today — the current system accepts only
four numeric fields with no identifiers and stores no request history by
default. If a future extension collected real behavioral data, it should:

- Be **opt-in**, with the user clearly told which fields are collected and
  why.
- Avoid collecting personally identifiable information; four numeric signals
  (focus/distraction minutes, task count, deadline hours) do not require a
  name, email, or device identifier to be useful.
- Minimize retention — do not keep raw per-request inputs longer than needed
  to serve the response and, if enabled, aggregate metrics.
- Give users visibility into and control over what's stored about them.

## What the running service currently logs and exposes

- **Metrics** (`/metrics`, Prometheus format): request counts/latency by
  route and status, and prediction counts by class and inference source
  (`kserve` / `model_local` / `rule` / `rule_fallback*`). Labels are bounded
  to these small fixed sets — no user IDs, request IDs, or raw feature values
  are ever used as metric labels (unbounded/high-cardinality labels would
  also be a Prometheus operational problem, not just a privacy one).
- **Logs**: structured application logs via Python's standard `logging`
  module. The service does not log raw request bodies, and `/model-info`
  deliberately omits the configured `KSERVE_PREDICT_URL` value itself
  (reports only whether one is set) to avoid leaking an internal endpoint.
- **Traces**: OpenTelemetry spans are emitted for the request lifecycle when
  tracing is enabled; span attributes should stay limited to operational
  metadata (route, status, inference source), not raw personal input values.
