Initial sandbox execution was denied loopback (`listen EPERM 127.0.0.1`); the reproduction and qualification used authorized local loopback permission, never remote D1.

The unchanged `0001_focus.sql` defines `events.lifecycle_sequence ON events(session_id, sequence) WHERE sequence > 0`. Its events table does not constrain event types itself. Worker `validateEvent()` accepts positive integer sequences for the five lifecycle types, and activity/label contracts omit a sequence field. `eventStatement()` persists those as `e.sequence || 0`. Thus **`WHERE sequence > 0` is the matching predicate**, not a predicate that assumes all events have sequence positions or adds a nonexistent outbox event-type column.

The isolated outbox now enforces one event ID and one positive lifecycle sequence per session, while permitting distinct zero-sequence activity and effort rows. `delivery_order INTEGER PRIMARY KEY AUTOINCREMENT` is an internal persisted insertion ordinal, separate from business sequence and payload. Both dispatchers choose the earliest eligible insertion and block it if an earlier unacknowledged insertion exists **in that session**. Equal timestamps and repeated zero sequences do not tie; retries, expired leases and dead letters retain their ordinal. Other sessions can progress. This is commit order, not event-time sorting or inferred window/rating causality; late observations remain late in the delivery stream. Lifecycle appends remain contiguous through the existing atomic session update/CAS guard. No contiguous-sequence check is applied to observations.

The prototype append helper now normalizes an absent observation sequence to storage zero without changing the payload, preserves label/window/reported-at columns, checks session ownership atomically, and leaves lifecycle state/last sequence/time unchanged for observations. Replay returns the existing helper result (`false`, meaning no insert) and retains the original event JSON, outbox row, digest, ordinal and identity; no replacement logical record is created. Event IDs/idempotency keys remain the replay keys. Lease fencing, retry thresholds/backoff, acknowledgments, dead-letter policy and reconciliation remain in force. The mock gateway now checks sequences by event type and accepts zero for the existing observation payload contract. It still rejects invalid lifecycle sequences and envelope/payload disagreement.

[Cloudflare migrations](https://developers.cloudflare.com/d1/reference/migrations/) records applied filenames in `d1_migrations`; normal repeat execution should find no pending migration. A migration failure should halt activation; any earlier successfully applied migration remains a separate state to inspect.

Preserve the failed SQL and object inventory for an explicit corrective forward migration or approved restore.

Before any future production change, capture an approved protected export and current Time Travel bookmark, verify restore support/retention and rehearse restoring to an isolated database. [Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/) is database-level point-in-time recovery, subject to retention; restoring an earlier state also rewinds unrelated writes after that point. ## Critical migration compatibility finding

There is **no production outbox migration** in the repository. The only proposed executable schema is G1B's isolated `0001_outbox.sql`; it has `UNIQUE(session_id, sequence)`. The current Worker writes lifecycle events with positive sequence, but `eventStatement()` writes `sequence || 0` for effort ratings and activity windows. Therefore every such event in one session has outbox sequence `0`. A production mutation that atomically inserts its event and corresponding outbox row would reject the **second** such event in the same session. Omitting the outbox insert would silently lose delivery, violating G1A's atomicity invariant. Existing D1 `events` permits multiple sequence-0 records and enforces uniqueness only for lifecycle sequence `> 0`, so the proposed outbox constraint is not backward compatible with the existing API contract.

A disposable **local Miniflare/workerd D1** test loaded the unchanged `0001_focus.sql` and test-only outbox schema, created one synthetic session, then attempted two synthetic `effort.reported` event/outbox atomic batches with distinct event IDs, idempotency keys and label IDs but the same session and sequence `0`. Results: event 1 committed; event 2 was rejected by outbox `(session_id, sequence)` uniqueness; persisted counts remained **1 event / 1 outbox row**. Atomic rollback worked, but the second valid business mutation would fail if this schema were applied. No deployed D1 was queried or migrated for this reproduction.

The outbox has an index on `(state,next_attempt_at,lease_until)` and a unique `(session_id,sequence)` index used by ordering checks. A replacement production design needs a distinct event identity for non-lifecycle rows, a partial or otherwise correct lifecycle ordering constraint, explicit causal rules for windows/ratings, and an index review under actual D1 query plans. It also needs an additive migration and Worker `db.batch()` integration for every selected event type, existing-data/backfill policy, no-data-loss rollback procedure and tests for multiple labels/activity windows. An additive table alone is not a qualified rollback plan; no production migration was applied.
