# Model Card — Cognitive Load Classifier

> **This is not a medical, psychological, neurological, workplace-surveillance,
> or diagnostic system.** It is an educational MLOps demonstration. Predictions
> should not drive high-impact decisions about any real person.

## Purpose

Classify a synthetic "cognitive load" signal into `LOW` / `MEDIUM` / `HIGH`
from four inputs (focus minutes, distraction minutes, tasks due, hours to
deadline). The purpose of this project is to demonstrate an end-to-end MLOps
pipeline (DVC → MLflow → FastAPI → KServe/local serving → Kubernetes →
observability), not to produce a validated cognitive-load instrument.

## Model type

`sklearn.pipeline.Pipeline([StandardScaler, RandomForestClassifier])`,
trained by [`scripts/train_model.py`](../scripts/train_model.py).

- `n_estimators`, `random_state`, `test_size`: read from `params.yaml`
  (`train:` section) — see [`data-card.md`](data-card.md) for reproducibility
  details.
- `class_weight="balanced"` to offset the label imbalance documented in the
  data card.

## Features (in this exact order — see `preprocessing_api/features.py`)

1. `focus_minutes`
2. `distraction_minutes`
3. `tasks_due`
4. `hours_to_deadline`
5. `focus_ratio` (derived)
6. `distraction_ratio` (derived)

Both the training script and the FastAPI serving code (`model_client.py`)
import `FEATURE_COLUMNS` and the ratio formula from the same
`preprocessing_api/features.py` module, so there is one source of truth for
feature order and no risk of training-serving skew from a copy-paste drift
between the two.

## Label-generation method — read before trusting the metrics below

Training labels come from the **same deterministic rule** the API uses as its
non-ML fallback path, not from any independent or externally validated source.
See [`data-card.md`](data-card.md) for the full explanation. **Practically,
this means the metrics below measure how well the model reproduces a known
formula from a partial/noisy view of its own inputs — not real-world
predictive validity.**

**Baseline comparison:** the model (0.910 accuracy) clears the majority-class

deterministic function of the model's own input features, so a model with
enough capacity should recover it closely. This comparison demonstrates the
model learned *something* beyond guessing the most common class; it does not
demonstrate real-world validity, because there is no real-world label to
compare against (see data card).

## Baselines considered

- **Majority-class baseline**: implemented and logged automatically by
  `train_model.py` on every run (`baseline_majority_class_accuracy` in
  `reports/metrics.json` and as an MLflow metric).
- A linear/logistic baseline was not added in this pass — the majority-class
  baseline is the one meaningfully required to sanity-check "is the model
  learning anything," and given the label circularity described above, a
  fancier baseline comparison would not change the external-validity
  conclusion.

## MLflow tracking

Every training run logs: `model_type`, `n_estimators`, `random_state`,
`test_size`, `feature_columns`, the git commit SHA (as a tag, when running
inside a git checkout), `accuracy`, `baseline_majority_class_accuracy`,
`macro_f1`, `weighted_f1`, the joblib artifact, and a registered
`mlflow.sklearn` model version under the name `cognitive-load-classifier`.

**Persistent vs. ephemeral MLflow**: CI (`.github/workflows/ci-cd.yaml`, `build`
job) starts a **self-contained MLflow tracking server for the duration of that
job only** (SQLite backend, local artifact root under the runner's temp dir),
trains against it, registers a model version, and downloads that exact version
back down via `scripts/download_model_from_mlflow.py` before the Docker build
— this genuinely exercises "pull the model from MLflow," verified in CI logs
(`Created version 'N' of model 'cognitive-load-classifier'` →
`Downloading MLflow artifact from models:/cognitive-load-classifier/N`).
It does **not** provide durable, cross-run experiment history — each CI run's
MLflow server and its history are destroyed with the runner. A real deployment
should point `MLFLOW_TRACKING_URI` at a persistent server (the Docker build
already supports this via `--build-arg MLFLOW_TRACKING_URI=... MODEL_URI=...`,
documented in the README's Docker Build section) if long-term experiment
history and model governance are required.

## Artifact and version metadata

`scripts/download_model_from_mlflow.py` writes a manifest sidecar file
(`<MODEL_PATH>.manifest.json`) recording `model_uri`, `source`
(`"mlflow"` or `"local-existing"`), `feature_columns`, `downloaded_at`, and
whether `MLFLOW_TRACKING_URI` was configured (not its value, since it may
point at an internal-only host). The running API exposes this via
`GET /model-info` alongside which `INFERENCE_MODE` is active and whether the
local model / KServe backend are currently usable.

## Serving modes

See the README's "Inference modes" section and
[`architecture.md`](architecture.md) for the full explanation of
`INFERENCE_MODE=auto|rule|local_model|kserve` and why `auto` (the default,
silent kserve→local_model→rule chain) is documented as a local-demo
convenience, not a production recommendation.

## Expected failure modes

- **Out-of-distribution inputs**: values far outside the synthetic generator's
  ranges (e.g. `hours_to_deadline` in the millions) are schema-valid but were
  never seen in training; the model will still return a class (RandomForest
  always predicts something) but with no accuracy guarantee at those extremes.
- **Corrupt or missing model artifact**: `predict_with_local_model` catches
  load/predict exceptions and returns `None`, which in `INFERENCE_MODE=auto`
  falls through to the rule engine, and in `INFERENCE_MODE=local_model`
  returns HTTP 503 unless `ALLOW_RULE_FALLBACK=true` is explicitly set.
- **KServe unreachable**: same pattern via `predict_with_kserve` /
  `INFERENCE_MODE=kserve`.

## Privacy considerations

The model consumes only four numeric fields per request; no identifiers, free
text, or device/location data are accepted by the API schema
(`preprocessing_api/schemas.py`). See [`responsible-use.md`](responsible-use.md).

## Intended use

- Educational demonstration of an MLOps pipeline end-to-end.
- Local development, coursework grading, and portfolio review.

## Prohibited use

- Employee performance evaluation or monitoring.
- Medical, psychological, or neurological assessment or diagnosis.
- Academic discipline or accommodation decisions.
- Any decision with material consequences for a real person.

## Retraining

```bash
uv run --extra dev dvc repro
# or directly:
uv run --extra dev python scripts/train_model.py \
  --input data/raw/sample_data.csv --output models/cognitive_load_model.joblib
```

Both read hyperparameters from `params.yaml` by default; override with CLI
flags (`--test-size`, `--random-state`, `--n-estimators`) if needed.
