# Model Card — Cognitive Load Classifier

The focus-session experiment pipeline has a separate target contract named
`self_reported_effort`; it is not implemented by or evidence for the currently
packaged synthetic-proxy classifier. Its 1–7 user rating and derived
LOW/MEDIUM/HIGH projection are documented in
[`focus-session/contracts.md`](focus-session/contracts.md). PR 5 produces only
local experimental candidates as documented in
[`focus-session/multimodal-experiments.md`](focus-session/multimodal-experiments.md).
PR 6 can package one synthetic candidate and serve it only in explicit local
test-fixture mode, as documented in
[`focus-session/model-packaging-serving.md`](focus-session/model-packaging-serving.md).
No focus-session model is approved, registered, promoted, or production-served.

> **This is not a medical, psychological, neurological, workplace-surveillance,
> or diagnostic system.** It is an educational MLOps demonstration. Predictions
> should not drive high-impact decisions about any real person.

## Purpose

Classify a synthetic "cognitive load" signal into `LOW` / `MEDIUM` / `HIGH`
from four inputs (focus minutes, distraction minutes, tasks due, hours to
deadline). The purpose of this project is to demonstrate an end-to-end MLOps
pipeline (DVC → MLflow → FastAPI → KServe/local serving → Kubernetes →
observability), not to produce a validated cognitive-load instrument.

## Model type

`sklearn.pipeline.Pipeline([StandardScaler, RandomForestClassifier])`,
trained by [`scripts/train_model.py`](../scripts/train_model.py).

- `n_estimators=200`, `random_state=42`, and `class_weight="balanced"` are
  recorded candidate parameters.
- The script groups rows by timestamp into chronological 60% training, 20%
  validation, and 20% previously observed audit partitions.

## Features (in this exact order — see `preprocessing_api/features.py`)

1. `focus_minutes`
2. `distraction_minutes`
3. `tasks_due`
4. `hours_to_deadline`
5. `focus_ratio` (derived)
6. `distraction_ratio` (derived)

Both the training script and the FastAPI serving code (`model_client.py`)
import `FEATURE_COLUMNS` and the ratio formula from the same
`preprocessing_api/features.py` module, so there is one source of truth for
feature order and substantially less copy-paste skew. Artifact signatures,
dependencies, package metadata, and deployment configuration still require
independent compatibility checks.

## Label-generation method — read before trusting the metrics below

Training labels come from the **same deterministic rule** the API uses as its
non-ML fallback path, not from any independent or externally validated source.
See [`data-card.md`](data-card.md) for the full explanation. **Practically,
this means the metrics below measure how well the model reproduces a known
formula from a partial/noisy view of its own inputs — not real-world
predictive validity.**

## Baselines considered

- **Dummy majority** and **logistic regression** are evaluated in
  `scripts/train_model.py` and recorded in `reports/metrics.json`.
- Each candidate is tracked with validation metrics and lineage in an isolated
  engineering experiment. No candidate is registered or approved.

## MLflow tracking

The current script logs candidate parameters, validation metrics, dataset and
split identities, feature schema, DVC and Git identities, code hashes, dependency
versions, and evaluation artifacts. It does not register, approve, or promote a
model.

**Persistent vs. ephemeral MLflow**: CI (`.github/workflows/ci-cd.yaml`, `build`
job) starts a **self-contained MLflow tracking server for the duration of that
job only** (SQLite backend, local artifact root under the runner's temp dir),
trains against it, logs isolated engineering candidates, and uses the directly
selected joblib for the non-production image build. It does not read or mutate
the production registry.
No specific retained hosted run was revalidated for this documentation change.
The workflow does **not** provide durable cross-run experiment history: each run's
MLflow server and its history are destroyed with the runner. A real deployment
should point `MLFLOW_TRACKING_URI` at a persistent server (the Docker build
already supports this via `--build-arg MLFLOW_TRACKING_URI=... MODEL_URI=...`,
documented in the README's Docker Build section) if long-term experiment
history and model governance are required.

## Artifact and version metadata

`scripts/download_model_from_mlflow.py` downloads or copies a model to
`MODEL_PATH`; it does not write a lineage sidecar. The strict production package
path is instead defined by `scripts/package_approved_model.py`, which requires
an exact model name/version and artifact-tree digest plus approval/provenance
metadata. The current registry versions do not satisfy that contract.

## Serving modes

The current API accepts `INFERENCE_MODE=demo_rule|local_model|kserve` and
defaults to `demo_rule`. `local_model` and `kserve` failures do not silently
fall back to the rule path. See [`architecture.md`](architecture.md).

## Expected failure modes

- **Out-of-distribution inputs**: values far outside the synthetic generator's
  ranges (e.g. `hours_to_deadline` in the millions) are schema-valid but were
  never seen in training; the model will still return a class (RandomForest
  always predicts something) but with no accuracy guarantee at those extremes.
- **Corrupt, missing, or provenance-mismatched local model**: explicit
  `local_model` mode fails rather than substituting a rule result.
- **KServe unavailable or provenance-mismatched**: explicit `kserve` mode
  returns the mapped failure response rather than changing inference mode.

## Privacy considerations

The model consumes only four numeric fields per request; no identifiers, free
text, or device/location data are accepted by the API schema
(`preprocessing_api/schemas.py`). See [`responsible-use.md`](responsible-use.md).

## Intended use

- Educational demonstration of an MLOps pipeline end-to-end.
- Local development, coursework grading, and portfolio review.

## Prohibited use

- Employee performance evaluation or monitoring.
- Medical, psychological, or neurological assessment or diagnosis.
- Academic discipline or accommodation decisions.
- Any decision with material consequences for a real person.

## Retraining

```bash
uv run --extra dev dvc repro
# or directly:
uv run --extra dev python scripts/train_model.py \
  --input data/raw/sample_data.csv --output models/cognitive_load_model.joblib
```

The DVC stage supplies input/output and registry names from repository
configuration. Model hyperparameters and the 80/20 split are currently
hard-coded in `scripts/train_model.py`; there are no hyperparameter override
flags.
